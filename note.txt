# 美股市場資料 ETL / Data Warehouse / Dashboard 專案筆記（重構版）

## 專案總目標

建立一套可重跑、可追溯、可擴充的美股資料 ETL / Data Warehouse / Dashboard 專案。

本專案不是單純抓股價或畫 K 線，而是以資料工程能力展示為主軸，逐步涵蓋：

- Extract：從資料來源擷取資料
- Transform：清洗、欄位標準化、格式轉換、衍生指標計算
- Validate：資料品質檢查，避免錯誤資料入庫
- Load / Upsert：寫入 PostgreSQL，並支援可重跑
- Observability：輸出任務摘要、成功/失敗狀態與 affected rows
- Data Warehouse：建立標準化資料模型與分析表
- CLI：讓 ETL 可透過 terminal 參數化執行
- 後續延伸：公司主檔、財報、新聞、Airflow、Dashboard、README 與面試包裝

---

## Phase 0：Docker + PostgreSQL 開發環境

### 本階段目標

建立一個可重現、可持久化、可被 Git 管理邊界保護的本機 PostgreSQL 開發環境。

### 技術節點

#### 1. 使用 Docker Compose 建立 PostgreSQL

透過 `docker-compose.yml` 啟動 PostgreSQL container，讓資料庫環境不依賴本機手動安裝。

目的：

- 降低環境安裝成本
- 讓專案可以在其他電腦上重現
- 未來可更容易與 Airflow、Dashboard 等服務整合

#### 2. 使用 `.env` 管理資料庫設定

將 DB 帳號、密碼、資料庫名稱等設定放在 `.env`，避免直接寫死在 `docker-compose.yml`。

目的：

- 避免敏感資訊進入 Git
- 保留本機環境設定彈性
- 未來可切換 dev / test / prod 設定

#### 3. 使用 volume / bind mount 保存 PostgreSQL 資料

將 PostgreSQL 實體資料掛載到本機目錄，例如 `.docker/postgres`。

目的：

- container 刪除後資料仍保留
- 避免每次重啟都重新建立資料庫
- 支援長期累積資料

#### 4. 使用 `db/init/*.sql` 初始化 schema

透過 `db/init/001_create_tables.sql` 建立 `daily_prices` table。

目的：

- 資料表 schema 可版本化
- 專案初始化流程可重跑
- 讓資料庫結構可被 README 與面試清楚說明

#### 5. 使用 `.gitignore` 管理 Git 邊界

排除：

- `.env`
- `.docker/`
- `data/raw/`
- `data/processed/`

目的：

- 避免敏感資訊進 Git
- 避免大量資料或本機狀態污染版本控制
- 保留程式碼、schema、文件的乾淨歷史

#### 6. 使用 DBeaver 驗證資料庫

透過 DBeaver 確認：

- database 是否建立成功
- schema 是否存在
- table 是否建立成功
- 欄位型別與主鍵是否正確

目的：

- 確認 DB 環境與 SQL 初始化有效
- 建立後續人工驗證基準

### 階段成果

完成 PostgreSQL 本機開發環境，具備資料持久化、敏感資訊管理與 schema 初始化能力。

## Phase 1：單支股票 OHLCV Extract → Transform → Validate → Load

### 本階段目標

建立單支股票從 yfinance 擷取、轉換、驗證到入庫的最小可行 ETL 流程。

### 技術節點

#### 1. 使用 yfinance 抓取單支股票 OHLCV

從 yfinance 取得 Open、High、Low、Close、Adj Close、Volume 等行情資料。

目的：

- 建立第一個資料來源
- 取得可被標準化的 raw market data

#### 2. 理解 yfinance MultiIndex columns

yfinance 在部分情境會回傳 MultiIndex columns，例如：

- level 0：Price 欄位，如 Open / High / Low / Close
- level 1：Ticker，如 AAPL / MSFT

目前處理方式：

- 移除 ticker level
- 保留價格欄位
- 將 Date index reset 成一般欄位

目的：

- 將 yfinance 特有格式轉換成標準 DataFrame
- 避免後續資料表欄位不一致

#### 3. 對齊 `daily_prices` schema

將 yfinance 欄位轉成資料表欄位：

| yfinance 欄位 | daily_prices 欄位 |
|---|---|
| Open | open_price |
| High | high_price |
| Low | low_price |
| Close | close_price |
| Adj Close | adjusted_close |
| Volume | volume |
| Date index | trade_date |

另外補上：

- `ticker`
- `source`

目的：

- 建立一致的資料模型
- 讓不同來源未來可以轉成相同格式
- 保留資料來源追蹤能力

#### 4. 將 `trade_date` 轉成 date

將 datetime 轉成 Python date，對應 PostgreSQL `DATE` 型別。

目的：

- 避免日期欄位混入時間資訊
- 讓 `(ticker, trade_date)` 可作為穩定主鍵

#### 5. 建立 `validate_daily_prices(df)`

檢查項目：

- 必要欄位是否存在
- ticker 是否空值
- trade_date 是否空值
- OHLC 是否空值
- volume 是否空值
- volume 是否 >= 0
- high_price >= low_price
- high_price >= open_price
- high_price >= close_price
- low_price <= open_price
- low_price <= close_price
- ticker + trade_date 是否重複

目的：

- 在資料入庫前擋住明顯錯誤
- 避免壞資料污染 Data Warehouse
- 讓 validator 後續可被多股票、CLI、Airflow 重用

### 階段成果

完成單支股票的標準 ETL 流程，將 raw market data 轉為可入庫的標準化資料模型。

## Phase 2A：多股票批次 Extract / Transform / Validate / Upsert

### 本階段目標

將單支股票 ETL 擴充成多股票批次處理，並做到單一 ticker 失敗不影響整批任務。

### 技術節點

#### 1. Extract 回傳成功與失敗結果

資料結構：

```python
{
    "AAPL": raw_df,
    "MSFT": raw_df,
}
```

失敗 ticker 額外記錄：

```python
{
    "FAKE123": "No data found"
}
```

目的：

- 成功資料與失敗原因分離
- 單一 ticker 失敗不會中斷整批 ETL
- 建立錯誤隔離能力

#### 2. Transform 使用 dict → long-format DataFrame

流程：

- `for ticker, raw_df in dfs.items()`
- `raw_df.copy()` 避免直接修改原始資料
- 處理 MultiIndex
- reset index
- rename columns
- 補 ticker / source
- 每支 ticker 結果放入 `frames`
- 最後使用 `pd.concat(frames, ignore_index=True)` 合併

目的：

- 將多支股票整理成一張 long-format 表
- 讓 validator 與 loader 可以共用單一資料格式
- 避免在迴圈中反覆 concat 造成效能與可讀性問題

#### 3. 共用 daily_prices validator 與 loader

多股票轉換完成後，仍然回到同一套：

- `validate_daily_prices(df)`
- `upsert_daily_prices(df)`

目的：

- 保持模組重用
- 減少重複邏輯
- 讓單支與多支 ETL 都使用一致資料品質規則

### 階段成果

完成多股票批次 ETL，具備錯誤隔離、long-format 標準化與共用 Validate / Load 流程。

## Phase 2B：Multi Stock ETL Summary / 批次任務摘要

### 本階段目標

建立 ETL Observability 雛形，讓每次批次任務的執行結果可觀察、可追蹤、可除錯。

### 技術節點

#### 1. Extract 階段回報成功與失敗 ticker

紀錄：

- success_tickers
- failed_tickers
- raw_rows_by_ticker

目的：

- 知道哪些 ticker 有資料
- 知道哪些 ticker 失敗與原因
- 避免只看到程式成功結束，卻不知道資料是否完整

#### 2. Transform 階段回報總筆數

紀錄：

- transformed_rows

目的：

- 確認資料是否成功轉成標準格式
- 與 raw rows 做基本比對

#### 3. Loader 回報 affected rows

`upsert_daily_prices(df)` 使用 `RETURNING` 回傳實際新增或更新的資料列。

目的：

- 判斷本次 ETL 是否真的改變資料
- 支援重跑時觀察 affected rows 是否為 0
- 建立可重跑性檢查基準

#### 4. Script 統整並印出 summary

摘要包含：

- Extract 起始日
- Extract 結束日
- Period
- Interval
- Total tickers
- Success tickers
- Failed tickers
- Transformed rows
- Affected rows
- Success ticker raw rows
- Failed ticker reason

目的：

- 建立任務層級的可觀察性
- 未來可延伸成 log、metadata table 或 Airflow task result

### 階段成果

完成多股票 ETL Summary，讓批次任務具有基本 Observability 與除錯能力。

## Phase 2C：日期區間 Backfill

### 本階段目標

讓 ETL 支援指定日期區間補載歷史資料。

### 技術節點

#### 1. Extract 支援 `start_date` / `end_date`

讓 yfinance extractor 可依指定日期區間抓資料。

目的：

- 支援歷史資料補載
- 不必每次只抓固定 period
- 建立未來增量更新與 backfill 的基礎

#### 2. 外層 script 決定預設 end_date

若有 `start_date` 但未指定 `end_date`，由 script 補今天日期。

目的：

- extractor 只負責依參數抓資料
- 避免 extractor 內部偷偷決定日期邏輯
- 保持模組職責清楚

#### 3. Upsert 支援重跑

相同資料重跑時 affected rows 應為 0。

目的：

- 確認 ETL 可以安全重跑
- 避免 backfill 重複寫入造成資料污染

### 階段成果

完成指定日期區間補載能力，並維持 upsert 可重跑特性。

## Phase 3A：建立 `technical_indicators` table

### 本階段目標

建立衍生分析表，用於保存從 `daily_prices` 計算出的技術指標。

### 技術節點

#### 1. 建立 `technical_indicators` 資料表

主鍵：

```text
ticker + trade_date
```

欄位：

| 欄位 | 意義 |
|---|---|
| ticker | 股票代號 |
| trade_date | 交易日 |
| sma_5 | 5 日簡單移動平均 |
| sma_20 | 20 日簡單移動平均 |
| sma_60 | 60 日簡單移動平均 |
| volume_avg_20d | 20 日平均成交量 |
| volume_ratio_20d | 當日成交量 / 20 日平均成交量 |
| source | 指標來源，例如 daily_prices |
| created_at | 第一次建立時間 |
| updated_at | 最近一次更新時間 |

目的：

- 將衍生指標與原始行情分離
- 建立可分析的 Data Warehouse 表
- 支援未來 Dashboard、策略分析與 SQL 查詢

#### 2. 使用 SQL 初始化表結構

透過 `db/init/002_create_technical_indicators.sql` 建立 schema。

目的：

- 讓資料庫結構可版本化
- 未來可被環境初始化流程重現

### 階段成果

完成 `technical_indicators` table，建立第一張衍生分析表。

## Phase 3B：從 `daily_prices` 計算 technical indicators DataFrame

### 本階段目標

從 `daily_prices` 讀取價格與成交量資料，計算技術指標 DataFrame。

### 技術節點

#### 1. 從 PostgreSQL 讀取必要欄位

讀取：

- ticker
- trade_date
- close_price
- volume
- source

目的：

- 只取計算技術指標所需欄位
- 降低資料處理複雜度

#### 2. 使用 `sort_values(["ticker", "trade_date"])`

目的：

- 確保每支股票依時間排序
- 避免 rolling window 使用錯誤順序計算

#### 3. 使用 `groupby("ticker")` 分組

概念：

```text
AAPL → AAPL 自己的時間序列
MSFT → MSFT 自己的時間序列
NVDA → NVDA 自己的時間序列
```

目的：

- 避免不同股票的價格資料混在一起計算 SMA

#### 4. 使用 `transform(lambda s: s.rolling(window).mean())`

功能：

- `s` 是單一 ticker 的 close_price Series
- `rolling(window=5)` 取當前列與前 4 列
- `mean()` 計算移動平均
- `transform()` 回傳與原 DataFrame 同長度的 Series，可對齊回原表

目的：

- 計算 SMA5 / SMA20 / SMA60
- 保留原始資料列對齊關係

#### 5. 計算成交量指標

包含：

- `volume_avg_20d`
- `volume_ratio_20d = volume / volume_avg_20d`

目的：

- 觀察成交量是否放大
- 為未來事件分析或 Dashboard 提供基礎指標

### 階段成果

完成 `calculate_technical_indicators(df)`，可從 daily_prices 計算技術指標 DataFrame。

## Phase 3C：technical_indicators Validate + Upsert

### 本階段目標

將 technical indicators DataFrame 進行資料品質檢查，並正式 upsert 到 PostgreSQL。

### 技術節點

#### 1. 建立 `validate_technical_indicators(df)`

檢查項目：

- 必要欄位是否存在
- ticker 不可空
- trade_date 不可空
- source 不可空
- ticker + trade_date 不可重複
- volume_avg_20d 若有值必須 >= 0
- volume_ratio_20d 若有值必須 >= 0
- SMA 前期 NaN 合理，不視為錯誤

目的：

- technical_indicators 是衍生表，但仍可能因 transform 邏輯錯誤而產生異常
- 入庫前需要獨立資料品質檢查
- 允許移動平均前期資料不足造成的合理 NaN

#### 2. 建立 `upsert_technical_indicators(df)`

使用：

- SQLAlchemy Core
- PostgreSQL `insert`
- `on_conflict_do_update`
- conflict key：`ticker + trade_date`

更新欄位：

- sma_5
- sma_20
- sma_60
- volume_avg_20d
- volume_ratio_20d
- source
- updated_at

目的：

- 資料不存在時 INSERT
- 資料已存在且內容不同時 UPDATE
- 資料相同時不 UPDATE
- created_at 保留首次建立時間
- updated_at 只在實際異動時刷新

#### 3. 使用 `is_distinct_from` 判斷差異

目的：

- 安全處理 NULL 比較
- 避免資料相同時仍刷新 updated_at
- 保持 ETL 重跑結果可觀察

#### 4. 建立測試 script 驗證 upsert

測試內容：

- 從 daily_prices 讀資料
- 計算 technical indicators
- validate 通過
- upsert 入 technical_indicators
- 查回資料確認寫入結果
- 第二次重跑 affected rows 應為 0

目的：

- 每個 loader / validator 都應有獨立測試入口
- 避免功能只在主流程中被動驗證

### 階段成果

完成 technical_indicators 的 Validate + Upsert，讓衍生技術指標正式進入 PostgreSQL。

## Phase 3D：technical_indicators ETL script / CLI 串接

### 本階段目標

將 technical indicators 的讀取、計算、驗證、upsert 流程整理成正式 CLI ETL script。

### 技術節點

#### 1. 建立 `scripts/run_technical_indicator_etl.py`

流程：

1. 解析 CLI 參數
2. 從 daily_prices 讀資料
3. 可指定 ticker
4. 可指定 output 日期區間
5. 計算 technical indicators
6. 依日期篩選本次要寫入的資料
7. validate
8. upsert
9. 印出 ETL summary

目的：

- 從測試 script 進化為正式 ETL 入口
- 未來可被 Airflow 或其他排程工具呼叫

#### 2. CLI 支援參數

支援：

- `--tickers`
- `--start-date`
- `--end-date`

目的：

- 可指定 ticker 重算
- 可指定本次輸出日期範圍
- 不需要修改程式碼即可操作 ETL

#### 3. 先讀完整 ticker 歷史資料，再篩 output 日期

因為 SMA60 需要前 59 筆交易資料，所以不能只讀指定日期區間。

目前策略：

1. 依 ticker 讀完整 daily_prices
2. 計算完整 technical_indicators
3. 再依 `start_date` / `end_date` 篩出本次要 upsert 的資料

目的：

- 避免 SMA 因前期資料不足而錯算
- 在目前資料量不大時，優先保證正確性

#### 4. Summary 統計 rows by ticker

使用：

```python
filtered_df.groupby("ticker").size().sort_index().to_dict()
```

目的：

- 顯示每支 ticker 本次輸出筆數
- 讓任務結果更容易檢查
- 每次排序穩定，方便重跑比對

### 階段成果

完成 technical_indicators ETL CLI，可正式重跑指標流程，並支援 ticker 與日期區間參數。
